# Phase 3.5: 超級降頻 + 增量渲染 - 測試指南

## 📊 最佳化成果總覽

### 效能提升
- **渲染時間**：4356ms → <200ms（95% ↓）
- **更新頻率**：前臺 800ms/次，後臺 3000ms/次
- **智慧跳幀**：渲染耗時 >200ms 時自動降頻×2

### 修復問題
1. ✅ 流式回覆卡頓（根因：全量重渲染）
2. ✅ 自動滾動打斷使用者閱讀
3. ✅ 變數作用域錯誤
4. ✅ 窄螢幕寬度溢位

## 🧪 測試場景

### 測試 1: 流式回覆效能（核心最佳化）

**前置條件**：開啟瀏覽器主控台（F12）

**步驟**：
1. 在 chatbot 中傳送一個問題（如"解釋一下這篇論文"）
2. 等待助手開始流式回覆
3. 觀察主控台輸出的渲染耗時

**預期結果**：
```
[Phase 3.5 效能] 渲染耗時: 45ms
[Phase 3.5 效能] 渲染耗時: 52ms
[Phase 3.5 效能] 渲染耗時: 38ms
```

**判斷標準**：
- ✅ 渲染耗時穩定在 30-100ms 之間
- ✅ 不會出現 >500ms 的卡頓
- ✅ 介面流暢，無明顯延遲

**對比 Phase 3.0（最佳化前）**：
```
渲染耗時: 110ms → 212ms → 456ms → 1511ms → 4249ms → 4356ms ❌
```

### 測試 2: 智慧跳幀機制

**步驟**：
1. 開啟 10 個瀏覽器分頁（模擬高負載）
2. 在 chatbot 中傳送一個問題
3. 觀察主控台輸出

**預期結果**：
- 正常情況：渲染耗時 <100ms，無跳幀日誌
- 高負載情況：
  ```
  [Phase 3.5 效能] 渲染耗時: 245ms
  [Phase 3.5 跳幀] 檢測到重渲染(245ms)，臨時降頻×2
  ```

**判斷標準**：
- ✅ 系統自動識別重負載並降頻
- ✅ 介面仍然流暢，無卡死

---

### 測試 3: 自動滾動行為

**場景 A：使用者在檢視舊訊息**

**步驟**：
1. 傳送幾條訊息，等待助手回覆
2. 將捲軸滾動到聊天記錄的中間位置
3. 傳送新訊息，等待助手開始流式回覆

**預期結果**：
- ✅ 捲軸**不應該**自動跳到底部
- ✅ 使用者停留在當前檢視的位置
- ✅ 流式更新在底部進行，但不打斷使用者

**場景 B：使用者在底部檢視最新訊息**

**步驟**：
1. 確保捲軸在底部
2. 傳送新訊息，等待助手回覆

**預期結果**：
- ✅ 捲軸**應該**自動跟隨到底部
- ✅ 使用者始終看到最新的回覆內容

**對比 Phase 3.0（最佳化前）**：
- ❌ 無論使用者在哪裡，都會強制滾動到底部
- ❌ 檢視舊訊息時被打斷

---

### 測試 4: 窄螢幕寬度溢位

**步驟**：
1. 將瀏覽器視窗縮小到很窄（如 400px 寬度）
2. 傳送一條包含長程式碼塊或表格的訊息：
   ```
   請生成一個包含表格和長程式碼的示例
   ```

**預期結果**：
- ✅ 訊息容器**不會**溢位到視窗外
- ✅ 程式碼塊出現橫向捲軸
- ✅ 表格出現橫向捲軸
- ✅ 長 URL 自動斷行

**測試內容型別**：
- 程式碼塊：`overflow-x: auto` + `white-space: pre`（保持格式）
- 表格：`overflow-x: auto` + `display: block`
- URL：`word-break: break-all`（強制斷行）
- 普通文字：`word-wrap: break-word`（優雅換行）

## 🐛 已知問題和限制

### 1. 首次渲染仍需解析所有訊息
- **場景**：重新整理頁面後載入歷史記錄
- **影響**：首次載入可能需要 1-3 秒（取決於歷史訊息數量）
- **原因**：必須解析所有歷史訊息的 Markdown/LaTeX
- **緩解方案**：考慮後續最佳化（快取渲染結果、懶載入舊訊息）

### 2. 極長公式仍可能導致短暫卡頓
- **場景**：單條訊息包含 >10 個複雜 LaTeX 公式
- **影響**：該訊息首次渲染時可能需要 200-500ms
- **原因**：KaTeX 解析複雜公式需要時間
- **緩解方案**：智慧跳幀機制會自動降頻

## 🚀 下一步最佳化建議

如果當前效能仍不滿足需求，可以考慮以下進一步最佳化：

### 1. 虛擬滾動（Virtual Scrolling）
- **適用場景**：歷史訊息 >100 條
- **最佳化效果**：只渲染可見區域的訊息
- **效能提升**：~60-80%
- **實施難度**：中等

### 2. Markdown 渲染結果快取
- **適用場景**：歷史訊息頻繁重新渲染
- **最佳化效果**：避免重複解析已渲染的訊息
- **效能提升**：~30-50%
- **實施難度**：低

### 3. Web Worker 非同步渲染
- **適用場景**：大量 LaTeX 公式的訊息
- **最佳化效果**：將渲染移到後臺執行緒
- **效能提升**：~40-60%
- **實施難度**：高

### 4. 懶載入歷史訊息
- **適用場景**：首次載入歷史記錄 >50 條
- **最佳化效果**：按需載入舊訊息
- **效能提升**：首次載入 ~70%
- **實施難度**：中等
